# Restaurant app design alternatives

Visual study only: no Auth, Supabase, real guests or live orders. User asked for comparative directions before application. Existing app and menus remain unchanged.

Framed-sheet direction, seed 547027360, adapted to the user's explicit palette references (including saturated/dark grounds). Five palette characters, one shared operational language. Keep colors from references; use a local Manrope Cyrillic font for legible daily work, Lora only for the product wordmark. Colors carry station progress and the next action. No wallpaper, gradients or decorative chart icons.

Signature: large table identity with TWO independently labelled kitchen/bar readiness tracks. This is specific to the user's service workflow and previous bug. Waiter asks what can be served; kitchen asks which items remain; owner asks how the shift performed; admin asks whose invitation awaits approval. Each role has a dedicated visual screen.

Desktop: gallery navigation outside a real iframe preview; standalone preview opens at full width. App canvas uses a 208px labelled sidebar and a 24px-gutter sheet. Queue has three equal columns (available width minus 2×16px, divided by 3). On mobile sidebar folds away, queue becomes a vertical list with scrollable state tabs; actions ≥44px.

All amounts derive from sample order lines. Analytics groups those lines; it is explicitly prototype data. No arbitrary growth arrows or invented business proof. Interaction examples: individual station completion, serve only after both stations, filter tables, open item details, admin request overlay, palette/role/device selection. Approvals and notifications in this prototype change local in-memory fixtures only.

Directions: A pine/clay (references 1/9); B cream/blue/orange (2/3); C burgundy/ice (6/7); D sage/sand/navy (4); E dusty blue/terracotta (8, with a rose companion from 5 only as a quiet secondary). Request a visual choice after presenting all five; do not replace the running app with an unchosen direction.
